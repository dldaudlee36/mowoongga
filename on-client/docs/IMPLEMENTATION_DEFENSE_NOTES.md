# 모웅가(mowoongga) 최종 제출용 구현 설명 및 질의 대응서

> **제출용 정리본 — 현재 확인 가능한 구현 범위와 검증 상태**  
> 이 문서는 심사·제출 때 구현 의도와 한계를 명확히 설명하기 위한 자료입니다. 통과를 보장하거나 아직 확인하지 않은 기능을 완료로 주장하지 않습니다. 보안 Agent의 이름은 문서와 제출 안내에서 **모웅가(mowoongga)**로 표기합니다. 이 이름 표기만으로 기존 파일명이나 실행 중인 앱 제목이 바뀌는 것은 아닙니다.

## 1. 제출 요약

모웅가(mowoongga)는 직원이 본인의 로그인·기기·세션 상태, 업무 앱 접속 판정, 접속 기록과 보안 알림을 확인하도록 돕는 보안 Agent 과제입니다. 학생 확장은 기존 서버와 엔진을 대신하지 않고, 전달받은 결과를 구분해 화면에 표시하는 역할을 합니다.

이번 제출 설명의 대상은 `on-client/student/extension.mjs`에 있는 **13~16단계 화면 함수**입니다. 현재 파일에서 `renderIdentity`, `renderDecision`, `renderEvents`, `renderStatus`의 구현을 확인했습니다. 다만 이 문서 작성 시 앱을 실행하거나 브라우저에서 동작을 시험하지 않았습니다.

| 항목 | 확인 가능한 내용 |
|---|---|
| 13단계 `renderIdentity` | 사용자·기기·세션 정보와 상태를 표시하고, 오류와 동작 모드를 구분합니다. |
| 14단계 `renderDecision` | 허용·거부·추가 확인·확인 불가 판정과 요청 실패를 구분합니다. |
| 15단계 `renderEvents` | 받은 기록을 최신순으로 보여 주고, 클라이언트 필터와 기록 상세를 제공합니다. |
| 16단계 `renderStatus` | 기기·세션·알림·진단 정보를 표시하고, 사용자가 누를 때 도움정보 복사를 시도합니다. |
| 미구현 함수 | `renderVulnerabilities`, `renderAiConnection`, `renderExplanation`, `renderAction`은 안내 문구를 반환합니다. 완료 기능으로 설명하지 않습니다. |
| 판정 상태 | 대화에서 알려 주신 내용으로 13~15단계 통과를 확인했다고 이해했습니다. 16단계의 공식 판정 결과는 이 문서 작성 시 제공되지 않았습니다. |
| 실행·시험 | 문법 검사, 앱 실행, 브라우저 확인은 수행하지 않았습니다. |

## 2. 구현 내용과 설계 근거

### 2.1 신원·기기·세션 표시 — `renderIdentity`

- 사용자 정보가 불러오는 중인지, 오류인지, 정상 자료가 도착했는지 나누어 표시합니다.
- 오류 문구에는 서버 연결 실패와 오류 메시지를 표시하며, 오류 분기에서는 이전 사용자 정보를 표시하지 않습니다.
- 기기와 세션 상태는 한국어 설명과 원래 상태 코드를 함께 보여 줍니다. 예: `점검 필요 (noncompliant)`, `사용 중 (active)`.
- `demo`, `disconnected`, `unknown` 동작 모드는 각각 예제 자료, 연결 없음, 확인 불가로 표시합니다.

**설명할 때의 경계:** 화면에 사용자·기기 정보가 보인다는 사실만으로 실제 로그인이나 서버 연결을 검증했다고 말할 수는 없습니다.

### 2.2 접속 판정과 요청 실패 구분 — `renderDecision`

- `idle`, `loading`, `error`, `ok` 상태를 구분해 표시합니다.
- `allow`, `deny`, `challenge`는 한국어 뜻과 영문 코드를 함께 표시합니다. 그 밖의 값은 확인 불가로 처리하며 허용된 것으로 보이지 않게 합니다.
- `challenge`는 추가 확인이 필요하다고 안내하고, 앱이 확인 절차를 대신하지 않는다고 명시합니다.
- 요청·네트워크 오류는 서버의 `deny` 판정과 별개의 실패로 표시합니다. 이유, 확인 시각, 앱 식별자도 표시합니다.

**설명할 때의 경계:** 이 함수는 전달받은 판정 결과를 표시합니다. 자체적으로 업무 앱 접근을 허용하거나 차단하는 보안 집행 코드는 아닙니다.

### 2.3 접속 기록과 상세 보기 — `renderEvents`

- 로딩, 조회 실패, 빈 기록을 서로 다른 문구로 표시합니다.
- 입력 배열의 복사본을 만들어 시각 기준 최신순으로 정렬합니다. 정렬 과정에서 전달받은 원본 배열을 직접 정렬하지 않습니다.
- 기록 종류·업무 앱·접속 상태 선택 상자를 제공하고, 선택이 바뀌면 이미 받은 자료만 브라우저 안에서 필터링합니다.
- 각 행에 사건 ID, 시각, 종류, 앱, 요약을 표시하고, 정해진 `data-student-event-id` 속성을 부여합니다.
- 상세 버튼은 상세 영역을 열고 닫습니다. 상세 영역에는 사건·앱 정보, 근거, 규칙, 접속·세션·기기 상태의 한국어 뜻과 원래 코드를 표시합니다.
- `supportedActions`가 있을 경우 해당 항목은 비활성 버튼과 미지원 안내로만 표시합니다. 조치 요청을 보내지 않습니다.

**설명할 때의 경계:** 목록은 전달받은 자료를 보여 주는 화면입니다. 새 XDR 탐지를 수행하거나 조직 전체 기록을 수집한다고 주장하지 않습니다. 실제 데이터 범위는 서버의 권한과 연결 결과를 따로 확인해야 합니다.

### 2.4 상태·알림·도움정보 — `renderStatus`

- 기기·세션 정보에서 로딩, 빈 목록, 오류를 나눕니다. 오류에는 수동 재시도 안내를 표시하며, 오류 처리 코드 자체가 자동 요청을 보내지는 않습니다.
- 기기·세션 상태는 한국어 뜻과 원래 코드를 함께 표시합니다. 세션 안내에는 현재 연결 하나를 표시하며 지난 세션 목록이 아니라는 점을 적습니다.
- 알림이 없으면 주의할 알림이 없다고 표시하고, 있으면 자료·코드·메시지를 글자로 보여 줍니다.
- 진단 화면은 정해 둔 필드(요청 ID, 버전, 확인 시각, 구성요소, 엔진 모드·코드)만 선택해 표시합니다. 값은 길이·제어 문자·일부 알려진 비밀 패턴을 검사하고, 사용자가 **“도움정보 복사”** 버튼을 누른 경우에만 해당 안전 필드의 복사를 시도합니다. 복사 성공·실패 상태도 화면에 표시합니다.

**설명할 때의 경계:** 비밀 패턴 검사는 완전한 비밀 탐지나 유출 방지 보장이 아닙니다. 알림의 자료·코드·메시지도 이 진단 필드 검사와 동일한 검사를 거치지 않으므로, 서버가 안전한 알림 데이터를 제공하는지 별도 확인해야 합니다. 클립보드 복사는 브라우저 권한과 실행 환경에 따라 실패할 수 있습니다.

## 3. 공통 안전 원칙

- 학생 화면 함수는 DOM 요소를 `document.createElement`로 만들고 표시 문자열은 `textContent`로 넣습니다. 외부 문자열을 HTML 마크업으로 해석하게 하는 방식은 사용하지 않습니다.
- 알 수 없는 판정, 오류, 빈 목록, 미지원 조치는 서로 합치지 않고 구분해 표시합니다.
- 화면 표시와 서버의 실제 보안 효과를 혼동하지 않습니다. 미지원 조치 버튼은 비활성 상태이며 실제 요청을 보내지 않습니다.
- 진단 정보는 제한된 필드만 사용하지만, 패턴 검사를 완전한 비밀 제거로 설명하지 않습니다.

이 원칙들은 확인한 학생 렌더링 코드의 표시 경로에 관한 설명입니다. 앱 전체의 보안이나 서버 동작을 이 코드만으로 증명하지는 않습니다.

## 4. 심사 질문에 대한 답변

### “허용·거부 화면이 있으니 접근 통제도 구현된 것인가요?”

아닙니다. `renderDecision`은 기존 서버에서 전달받은 판정을 보여 주는 UI입니다. 접근 허용·차단은 기존 엔진과 서버의 책임이며, 실제 연결과 집행 여부는 별도 환경에서 검증해야 합니다.

### “요청 오류와 서버의 접근 거부를 어떻게 구별하나요?”

접근 거부는 서버 판정값 `deny`이고, `status === 'error'`는 요청 또는 네트워크 실패입니다. 화면에서 별도 분기와 문구로 표시하므로 요청 실패를 거부 판정으로 바꾸지 않습니다.

### “판정을 알 수 없으면 허용으로 간주하나요?”

아닙니다. 알려진 판정값이 아닌 경우 확인 불가로 표시하고, 허용되지 않음·판정 불명이라는 의미를 함께 전달합니다. 다만 화면 문구가 서버 측 접근 제어를 대신하지는 않습니다.

### “기록이 없다는 것과 기록 조회 실패는 같은가요?”

아닙니다. 정상 응답에 기록 배열이 비어 있으면 기록 없음으로, 조회 자체가 실패하면 오류와 메시지로 표시합니다. 빈 목록을 실패로, 실패를 빈 목록으로 처리하지 않습니다.

### “필터를 바꿀 때 서버에 다시 요청하나요?”

현재 구현에서는 선택 상자의 변경 이벤트가 이미 전달된 배열을 브라우저 안에서 필터링합니다. 필터 변경만으로 서버에 다시 요청하지 않습니다. 실제 요청 동작은 앱 실행 후 네트워크 기록으로 별도 확인해야 합니다.

### “상세 보기나 미지원 조치 버튼이 실제 조치를 실행하나요?”

아닙니다. 상세 버튼은 상세 영역의 표시 여부만 바꿉니다. 미지원 조치 버튼은 비활성 상태이고 안내 문구를 함께 표시하며, 실제 요청을 보내지 않습니다.

### “도움정보 복사에서 비밀이 절대 노출되지 않나요?”

그렇게 보장할 수는 없습니다. 정해 둔 진단 필드와 몇 가지 값 검사를 사용하지만, 이는 완전한 비밀 탐지기가 아닙니다. 서버 응답이 안전한 필드만 포함하는지 확인하고, 복사하거나 공유하기 전에는 내용을 직접 살펴야 합니다.

### “실제 브라우저에서 검증했나요?”

아닙니다. 이번 문서 정리에서는 프로젝트 파일의 구현 내용을 검토했을 뿐, 문법 검사나 앱 실행, 브라우저 조작은 하지 않았습니다. 따라서 실제 화면 동작과 브라우저 호환성은 아직 확인되지 않았습니다.

## 5. 제출 전 직접 확인할 항목

아래 항목은 제출 전에 앱을 실행해 직접 확인하고, 확인하지 못한 것은 미확인으로 남깁니다.

1. 신원 화면에서 로딩·정상·오류가 각각 구분되고, 오류 전환 뒤 이전 사용자 정보가 남지 않는지 확인합니다.
2. 접속 판정에서 허용·거부·추가 확인·확인 불가와 요청 실패가 서로 다르게 보이는지 확인합니다.
3. 기록의 최신순 정렬, 세 필터, 빈 목록·오류 구분, 상세 열기·닫기를 확인합니다.
4. 상태 화면의 기기·세션 로딩·빈 목록·오류, 시간 초과 안내, 수동 재시도 문구를 확인합니다.
5. 미지원 조치 버튼이 비활성인지 확인하고, 개발자 도구 네트워크 탭에서 실제 요청이 발생하지 않는지 살펴봅니다.
6. 도움정보 복사 전후의 화면 상태와 복사된 내용에 민감정보가 없는지 확인합니다. 클립보드 권한이 거부될 때 실패 안내도 확인합니다.
7. 실제 서버 연결과 예제 자료·연결 없음 상태를 구분해 기록합니다. 예제 자료는 실제 연결 증거로 적지 않습니다.

## 6. 구두 설명 예시

> 모웅가(mowoongga)의 학생 확장은 보안 엔진을 대신하는 코드가 아니라, 서버가 전달한 사용자 상태·접속 판정·기록을 구분해 보여 주는 UI 계층입니다. 요청 실패와 접근 거부, 빈 기록과 조회 실패, 확인 불가와 허용을 서로 다르게 표시합니다. 기록 필터는 받은 자료 안에서 동작하며 미지원 조치는 비활성 안내로만 나타냅니다. 진단 복사는 정해 둔 필드만 사용자가 눌렀을 때 시도하지만, 값 검사가 완전한 비밀 탐지라고 주장하지 않습니다. 실제 서버 권한과 브라우저 동작은 별도로 확인해야 하며, 미구현 함수와 실행하지 않은 테스트는 완료로 말하지 않습니다.

## 7. 제출 상태 표기 원칙

- 13~15단계 공식 통과는 대화에서 전달받은 사용자 보고에 근거한 내용이며, 이 문서 작성자가 포털에서 직접 조회한 결과가 아닙니다.
- 16단계 구현 코드는 파일에서 확인했지만, 공식 제출·판정 결과는 확인하지 않았습니다.
- 브라우저 실행, 자동 검사, Git 커밋·푸시, 포털 제출 여부는 실제 결과를 확인하기 전까지 완료로 표시하지 않습니다.
- `renderVulnerabilities`, `renderAiConnection`, `renderExplanation`, `renderAction`은 현재 미구현 안내 상태입니다. 17~22단계 또는 전체 제품이 완성되었다고 주장하지 않습니다.
- 검증 과정에서 비밀번호·토큰·키·개인 인증정보를 문서, 캡처, 로그에 포함하지 않습니다.
